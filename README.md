# Metro obstacle detector — ROS 2 Humble

Обнаружение посторонних объектов в габарите пути по 3D-лидару. Подход без
обучения на объектах: **описываем нормальный тоннель (рельсы, стены, габарит)
и ищем всё, что в него не вписывается**, с подтверждением во времени.

## Быстрый старт (Docker)

```bash
cd hack_ws
docker build -t metro-obstacle .
xhost +local:docker   # для RViz
docker run --rm -it --net=host -e DISPLAY=$DISPLAY -v /tmp/.X11-unix:/tmp/.X11-unix \
  -v /absolute/path/to/doubleT_obstacle:/data/bag:ro metro-obstacle \
  ros2 launch metro_obstacle_ros demo.launch.py bag_path:=/data/bag \
  bag_topic:=/sensing/lidar/hesai128/pointcloud fixed_frame:=lidar_livox
```

Без RViz: добавьте `rviz:=false`. Для записей с топиком `/lidar_points`:
`bag_topic:=/lidar_points fixed_frame:=hesai_lidar`.

Без Docker: `source /opt/ros/humble/setup.bash && rosdep install --from-paths src
--ignore-src -y && colcon build --symlink-install && source install/setup.bash`.

## Алгоритм

1. **Предобработка**: невалидные точки, лидар → система поезда, обрезка вперёд.
2. **Ось пути вблизи** (≈50–70 м): плоскость пути + поднятые головки рельсов,
   сглаживание во времени через регистрацию прошлой оси к новым измерениям.
3. **Ось пути вдали — по стенам тоннеля** (новое). При скользящем падении луча
   рельсы пропадают на ~55 м, а стены видны на сотни метров. На участке с
   рельсами калибруется расстояние «ось пути → ближайшая конструкция стены»
   слева/справа; дальше коридор ведётся слоями вдоль стен (прогноз с постоянной
   кривизной + ворота по инновации, достаточно одной стены, слой растёт до 40 м
   там, где точек мало). После последнего измерения — короткая экстраполяция
   (80 м на прямой, 30 м в кривой), только если конец оси хорошо определён и
   ни один слой со стенными точками ей не противоречит.
4. **Модель нормального сечения пути** (по реальным записям): путь не плоский —
   поперечный уклон (один рельс выше), лоток посередине, полки. Для каждого
   бина 0.1 м по поперёк оси берётся высота поверхности в 1-метровых срезах и
   медиана по срезам (объект занимает мало срезов и в модель не попадает),
   со сглаживанием во времени. Высота точек считается от этой поверхности,
   поэтому рельсы, уклон и лоток не дают ложных «низких объектов».
5. **Габарит по постоянным конструкциям**: поезд проходит этот тоннель, значит
   сплошные конструкции у пути (служебный проход, край платформы) задают
   реальную границу. Вблизи измеряется ближайшая сплошная конструкция по
   сторонам и высотам (медиана по метровым срезам), и в каждом 5-метровом
   срезе, где она видна (занимает ≥40% длины среза), граница ставится от неё
   с запасом 0.15 м. Дальше 45 м и за рельсами габарит сужается ещё на 0.2 м
   (погрешность оси).
6. **Накопление 3 кадров** с компенсацией движения вдоль пути. Скорость поезда
   оценивается без одометрии — по смещению выступов стены (кронштейны, короба);
   гладкая стена и развёртка лидара не двигаются и исключаются. На реальных
   записях оценка даёт 15–19 м/с в движении и 0 при остановке.
7. **Кластеризация** DBSCAN с eps, растущим с дистанцией. Бракуются: длинные
   конструкции, плоские поверхности, мало точек для дистанции, кластеры без
   точек текущего кадра, касания края габарита, части внешних конструкций
   (кластер продолжается за границей — платформа, проход, стена), а за
   рельсами — объекты ниже 0.8 м, «висящие» выше 1.2 м и объекты в последних
   10 м измеренного коридора (там луч обычно упирается в стену кривой).
   Низкие объекты (<0.5 м) — только до 35 м, где пол измерен.
8. **Трекер**: подтверждение 2/3 (<40 м), 3/5 (40–120 м), 4/6 (>120 м), проверка
   устойчивости положения; подтверждённый объект не сбрасывается, если на
   кадр укоротилась зона обзора (ведение до 5 кадров).
9. **Результат**: ближайший объект, категория, уверенность, TTC, тормозной путь,
   флаг торможения.

Все параметры — в `src/metro_obstacle_ros/config/detector.yaml` (каждое поле
`config.py` — ROS-параметр с тем же именем; раньше большинство параметров из
YAML алгоритмом игнорировалось).

## Эксперименты на реальных записях (`tools/bag_to_npz.py` + `tools/eval_frames.py`)

Все 5 записей из архива организаторов (1611 кадров), без подстройки под
отдельный bag. Облака читаются прямо из `.db3` (нужны только sqlite и NumPy).

| Запись | Сцена | Исходная версия | Новая версия |
|---|---|---|---|
| doubleT_obstacle | человек переходит путь на 55–57 м, поезд стоит | 42 кадра, первый — 19-й | 47 кадров, первый — 16-й, 0 ложных |
| doubleT_platform | подъезд к станции, остановка | 0 ложных | 0 ложных |
| roundT_doubleT | переход круглый → двухпутный, 15–19 м/с | 0 ложных | 0 ложных |
| roundT_pressureGate_roundT | гермозатвор | 1 ложный кадр | 1 ложный кадр |
| roundT_squareT_pressureGate_squareT (a, b) | смена сечений, гермозатвор | 13 ложных кадров | 0 ложных |
| **Итого ложных кадров** | | **14** | **1** |

Измеренный коридор (где разрешена тревога): рельсы 40–70 м, дальше по стенам
до 77–175 м (зависит от кривой и сечения). Задержка: медиана ~100–115 мс
(p95 ~140–160 мс) на кадр на 2 медленных ядрах облачной машины на полном облаке
Hesai-128 (~300 тыс. точек); на симуляторе (меньше точек) ~55–60 мс. На стенде
i7-9700E (8 ядер) не измерялась. Дальнейшее ускорение — перенос геометрии пути
в отдельный поток / C++. Конвейер оптимизирован без изменения решений: на всех
шести записях результаты совпадают с версией до оптимизации.

Что выяснилось на реальных данных (и чего не было видно на симуляторе):
- путь с поперечным уклоном и лотком → появилась модель сечения пути;
- служебный проход на 1.1–1.4 м от оси → границу габарита задают постоянные
  конструкции, а не константа;
- в двухпутном тоннеле с одной стороны нет стены, стены неровные (шкафы на
  1.7–2.35 м) → по стене берётся медиана, калибруется только сплошная сторона;
- в переходной кривой экстраполяция оси по прямой даёт ложные цели →
  экстраполяция выключена, тревога только в измеренном коридоре;
- на станции уровень пола «подхватывался» с платформы, а разреженный слой
  стены на 190 м изгибал коридор → ограничения уровня и длины слоя.

В записях нет препятствия дальше 57 м, поэтому дальность на реальных данных
проверить нечем. На симуляторе (поезд стоит): человек — 100 % на 30 и 60 м,
56 % на 100 м, дальше не подтверждается; ящик 0.5 м — на 30 м, дальше нет
(объекты ниже 0.5 м дальше 35 м сознательно не подтверждаются: снижение порога
до 80 м даёт +10 ложных кадров на реальных записях). Дальняя цель (>120 м)
подтверждается только если край измеренного коридора стабилен 6 кадров
(`far_stable_range`) — это убрало 4 ложных кадра в конце squareT_a.
Валидации на отложенной выборке нет: пороги подбирались на этих же шести записях.
